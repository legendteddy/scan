# Scan 0.6.0 release candidate validation

This branch prepares the Scan 0.6.0 release candidate for owner review. It does **not** authorize or perform a tag, GitHub Release, PyPI publication, announcement, or any other release action.

## Candidate identity

- Project: `scan-skill`
- Candidate version: `0.6.0` (`scan 0.6.0`)
- Stable release currently published before this candidate: `0.5.0`
- State schema for new Scan outputs: `1.4`

Package metadata, `scan_core.version.__version__`, and the installed `scan --version` command must all agree on `0.6.0` for the exact candidate tree.

## Required source-tree gates

The exact release-candidate PR head must pass:

- the complete Python test suite;
- `git diff --check`;
- compile/import checks used by CI;
- ScanBench v1;
- ScanBench 2 corpus validation with 26 projects / 209 conditions and no blended quality score;
- evidence federation, observed evidence, handoff, Inspection Bundle, feedback/outbox, trust-boundary, and cross-layer contract tests;
- static report browser acceptance;
- optional MCP bridge validation;
- Python 3.11 and 3.13 compatibility.

## Required package gates

Build one wheel and one source distribution from the exact candidate tree. Verify:

- distribution project name is `scan-skill`;
- wheel and sdist metadata report version `0.6.0`;
- a fresh environment installs the built artifact successfully;
- installed runtime metadata equals `scan_core.version.__version__`;
- installed `scan --version` reports `scan 0.6.0`;
- installed `scan-bundle` is present;
- ScanBench 2 ground-truth data is packaged without setuptools package-discovery ambiguity.

## Installed v0.6 acceptance

Run `python scripts/v06_acceptance.py` against the installed candidate. The gate uses only synthetic temporary input and must verify:

1. offline state creation and validation with no Scan target execution or network use;
2. deterministic `scan handoff` bound to the exact base state/snapshot with no source bytes or raw evidence-result payloads;
3. `scan import-evidence` exact state/snapshot/artifact binding and no whole-project completeness upgrade;
4. `scan import-observed` exact binding, bounded control import, `authorization_attestation.verified_by_scan=false`, and no target/network execution by Scan during import;
5. `scan-bundle create` and `scan-bundle verify` exact state/handoff identity with no target/network execution during verification;
6. privacy-safe agent feedback receipt creation with `--submit never`, canonical receipt plus local outbox copy, and fail-closed unauthorized flush behavior;
7. packaged ScanBench 2 corpus summary of 26 projects / 209 conditions with `no_blended_quality_score=true`.

The native Windows, macOS and Linux release gates must run this installed-artifact acceptance path successfully.

## Evidence and maturity boundaries

A green release candidate establishes that these contracts and gates behave as tested. It does **not** establish:

- that every possible defect is detectable;
- that the 26/209 public corpus alone proves real-world effectiveness;
- that independent review coverage is complete;
- that holdout custody was genuinely external unless separate custody evidence exists;
- that imported specialist or observed evidence is independently reproduced by Scan;
- that an authorization attestation identifies an authenticated human/workflow unless separate evidence establishes that identity;
- whole-project release clearance when coverage or unknowns remain incomplete.

These dimensions remain separately reportable and must not be collapsed into a global trust/health score.

## Release authorization boundary

After the release-prep PR is merged and all exact-candidate validation is green, creating `v0.6.0`, publishing a GitHub Release, and allowing Trusted Publishing to upload to PyPI are still separate consequential actions.

Do not perform those actions until the repository owner explicitly approves the v0.6.0 release.
