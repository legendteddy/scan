# v0.6 semantic-work receipt contract

Status: development slice.

## Purpose

A semantic-work receipt records what an AI host or agent says it actually consumed during one Scan semantic-review run. It exists to measure repeated work without making Scan depend on a model provider or estimating token usage from file size.

The receipt is a sidecar. It does **not** change Scan schema 1.4, add canonical evidence, upgrade coverage, or prove that a semantic conclusion is correct.

## Format

```json
{
  "schema_version": "scan-semantic-work-receipt-1",
  "scan_id": "scan:...",
  "snapshot_digest": "sha256:...",
  "producer": {
    "name": "example-host",
    "model": "example-model"
  },
  "artifacts": [
    {
      "artifact_id": "artifact:...",
      "action": "fresh_read",
      "access_count": 2
    },
    {
      "artifact_id": "artifact:...",
      "action": "verified_reuse",
      "access_count": 1,
      "evidence_ids": ["evidence:..."]
    }
  ],
  "usage": {
    "provider": "example-host",
    "model": "example-model",
    "input_tokens": 12345,
    "output_tokens": 678
  }
}
```

`producer.name` is required. `producer.model` and `producer.version` are optional. The producer describes the host or agent that generated the telemetry; it is not treated as a trusted scanner identity.

## Artifact actions

Each artifact may appear once.

- `fresh_read` means the host reports that current target content for that canonical artifact was read during this semantic run.
- `verified_reuse` means the host reports that it consumed prior analysis instead of freshly reading that artifact. The row must reference canonical evidence IDs whose `inspection_origin` is already `verified_reuse` for the same artifact. The receipt cannot create or upgrade reuse authority by itself.
- `access_count` is an exact host-reported positive integer. A value greater than 1 exposes repeated access to the same artifact. Scan does not infer this number.

If an artifact was both freshly read and supported by old evidence, record it as `fresh_read` for efficiency measurement. The receipt is measuring current semantic work, not every provenance fact in the final state.

## Binding and validation

The receipt must match both `run.scan_id` and `provenance.snapshot_digest` from the validated canonical Scan state supplied to the benchmark. Every `artifact_id` must exist in that state.

For `verified_reuse`, every referenced evidence ID must exist, belong to the same artifact, and already be canonical `verified_reuse`. Unknown artifact IDs, stale snapshots, duplicate artifact rows, invalid reuse claims, and unsupported fields are rejected.

Receipts are bounded to 2 MB and 50,000 artifact rows in this slice.

## Exact token usage

`usage` is optional. When present it uses the same exact-host-usage contract as the v0.6 efficiency benchmark. Scan accepts reported non-negative token counts; it does not estimate missing counts.

If `total_tokens` is absent while exact `input_tokens` and `output_tokens` are present, the benchmark may calculate only their arithmetic sum and marks it as derived. No percentage saving is calculated automatically.

The existing standalone `--usage LABEL=JSON` input remains supported. Do not provide both standalone usage and embedded receipt usage for the same benchmark label.

## Benchmark use

```bash
python scripts/benchmark_efficiency.py \
  --run baseline=.scan/baseline-state.json \
  --run repeat=.scan/repeat-state.json \
  --work baseline=.scan/baseline-work.json \
  --work repeat=.scan/repeat-work.json \
  --pretty
```

The benchmark reports:

- fresh-read artifact count;
- fresh-read access count;
- repeated fresh-read access count;
- canonical verified-reuse artifact/access counts referenced by the receipt;
- the exact artifact IDs in each group;
- raw deltas between benchmark runs;
- exact token deltas only when comparable host usage exists.

## Trust boundary

A semantic-work receipt is **host-reported telemetry**, not canonical proof of semantic quality. Binding it to the Scan state prevents accidental comparison against another run and requiring canonical evidence for reuse prevents the sidecar from inventing verified reuse, but Scan cannot independently prove that a remote model truly read content exactly as reported.

Therefore:

- never use a receipt to set `coverage.analysis_complete` or `checks_complete`;
- never turn a receipt into findings, controls, or evidence automatically;
- never infer safety or finding quality from lower work counts;
- never estimate missing artifact accesses or token counts;
- compare findings, unknowns, and coverage alongside efficiency metrics before claiming an optimization is better.
