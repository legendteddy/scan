# Scan v0.4 MCP foundation

Status: **development slice; not a v0.4 release approval**

This document defines the first v0.4 implementation slice: a portable, read-only Model Context Protocol (MCP) bridge for Scan Core. The goal is to make Scan's deterministic evidence layer directly usable by compatible AI hosts without pretending that deterministic inventory is itself semantic analysis.

## Product outcome

A compatible MCP host can start Scan for one explicitly authorized project root and then:

- obtain a concise Scan summary for the current server snapshot;
- explicitly refresh a coverage-mode snapshot when current bytes are needed;
- page through the canonical artifact inventory consistently within that snapshot;
- obtain the complete canonical Scan 1.4 state when needed;
- request bounded UTF-8 artifact text through Scan's existing path-safety and redaction controls;
- receive a Scan review prompt that preserves the distinction between inventory, semantic review and runtime verification.

The MCP bridge does **not** autonomously produce semantic findings, execute target code, repair a project, open a network listener, or turn unassessed checks into passed checks.

## Installation boundary

The base `scan-skill` package remains dependency-free. MCP support is an optional extra:

```bash
pip install "scan-skill[mcp]"
```

During v0.4 development from a source checkout:

```bash
pip install -e ".[mcp]"
```

The optional extra uses the official Python MCP SDK major version 2. The console entry point is:

```bash
scan-mcp /path/to/project
```

`scan-mcp` uses the SDK's default stdio transport. It does not bind a TCP port.

## Root and filesystem authority

The project root is fixed when `scan-mcp` starts. It is resolved strictly and must be a directory. MCP tool calls cannot replace or broaden that root.

Artifact reads accept normalized project-relative locators only. They reject:

- absolute paths;
- parent traversal (`..`);
- empty or dot path components;
- Windows drive/alternate-stream colon syntax;
- NUL characters;
- links/reparse points rejected by Scan's bounded auxiliary reader;
- artifacts that are absent from the current deep server snapshot;
- non-regular files;
- incomplete/unhashed identities;
- binary or non-UTF-8 text for the text-read tool.

Each permitted text read is bounded to at most 1,000,000 bytes and verifies the safely opened bytes against the SHA-256 identity from the current deep server snapshot before returning content. A mismatch returns a stale result instead of mixing snapshots; `scan_refresh` is then the explicit way to establish a new snapshot.

## Privacy and host boundary

Artifact text is passed through Scan's existing deterministic redaction policy before it leaves the Scan MCP tool. `standard` is the default; `strict` can additionally redact supported email, phone and identifier patterns. Configured sensitive-path patterns block artifact text entirely and redact the locator in the blocked result.

The Scan MCP process itself performs no network egress and uses Core with `privacy_mode="offline"`, no baseline reuse and no project output files.

This does **not** mean the overall AI session is offline. The MCP host or model provider may transmit tool outputs according to its own architecture, settings and policy. Users must treat host-side data handling as a separate trust boundary.

## Tools

### `scan_summary`

Returns a concise deterministic summary for the current server snapshot. The first call for a coverage mode lazily creates that snapshot. It exposes both:

- `scan_mode`: coverage mode (`quick`, `deep`, or `forensic`); and
- `inspection_mode`: Core mechanism (`static`).

It also exposes `target_executed`, discovery/analysis completeness, check accounting and privacy/egress metadata. This prevents a deep inventory request from being mistaken for dynamic/runtime verification.

### `scan_refresh`

Explicitly rebuilds one coverage-mode snapshot and returns its new summary. The server keeps one in-memory snapshot per coverage mode so pagination and subsequent artifact reads refer to stable inventory identities instead of silently rescanning between calls.

### `scan_inventory`

Returns one page of canonical artifact records. `offset` is non-negative and `limit` is 1-250. The response includes the snapshot digest and next offset.

### `scan_state`

Returns the complete canonical Scan 1.4 deterministic state for the current server snapshot. This may be large. Agents should normally start with `scan_summary` plus paginated `scan_inventory` and request the full state only when the canonical handoff is useful.

### `scan_read_artifact`

Returns one bounded, digest-verified, redacted UTF-8 artifact. It never follows a call-supplied path outside the fixed root. Blocked and stale reads return structured reasons rather than raw exceptions or partial content.

## Resource and prompt

`scan://about` describes the trust boundary of the running server.

`scan_review` guides a compatible agent to account for all required Scan check categories, read relevant first-party content, preserve blocked/unverified areas, and avoid target-code execution unless separately authorized.

The prompt is guidance, not proof that the host actually completed those checks. Final semantic state still requires evidence-linked agent judgment and Scan validation.

## Non-goals for this slice

This slice intentionally does not add:

- remote HTTP/SSE/streamable-HTTP hosting;
- authentication for a network service;
- target-code execution or automatic tests/builds;
- autonomous model-provider execution inside Scan;
- semantic state mutation tools;
- automatic HTML report authoring from model judgments;
- external scanner adapters;
- project modification tools;
- a v0.4 version bump or release.

## Acceptance gates

The slice is ready for merge only when:

1. the base package still imports and tests without the optional MCP dependency;
2. a built wheel installed with the `mcp` extra exposes `scan-mcp`;
3. an in-memory official MCP client can list and call the Scan tools;
4. traversal, sensitive paths, binary content and configured byte ceilings are blocked;
5. credential redaction and strict personal-data redaction are exercised;
6. a successful MCP session creates no `.scan` directory or other target output;
7. the full existing Core regression suite still passes;
8. source files remain plain UTF-8 without BOM;
9. CI includes a dedicated MCP integration gate without adding MCP dependencies to ordinary Core jobs.

## Continuation after the foundation

The next v0.4 slices can build on this evidence bridge rather than embedding a model provider into Scan Core. Candidate follow-ons include portable host configuration/install guidance, a carefully bounded semantic-state continuation surface, ScanBench Agent-Honesty coverage, and optional adapter/import surfaces. Each should preserve the current rule: evidence depth must never be upgraded merely because an agent or protocol is present.
