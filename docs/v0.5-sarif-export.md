# Scan v0.5 SARIF export contract

Status: v0.5 development slice.

## Purpose

This slice adds deterministic SARIF 2.1.0 export on top of canonical Scan state. It is an interoperability layer for CI/code-scanning consumers; it does not create new findings, execute target code, infer runtime behavior, or replace Scan state/report evidence.

```bash
scan sarif .scan/state.json --output .scan/results.sarif
scan sarif .scan/state.json --output .scan/results.sarif --pretty
```

The input must first pass the existing Scan state validator. Export is deterministic for the same canonical state and Scan version.

## Evidence boundary

Only records in `state.findings` become SARIF `results`.

The exporter deliberately does **not** turn any of these into code-scanning alerts:

- unknowns;
- controls;
- unassessed or blocked checks;
- coverage gaps;
- inventory-only artifacts;
- the absence of findings.

Those remain visible in canonical Scan state/report. The SARIF run includes counts and an explicit export-policy property so an empty SARIF result set cannot honestly be interpreted as a complete Scan audit or security clearance.

## Mapping

- SARIF version: `2.1.0`.
- Tool: `Scan`, with the installed Scan semantic version.
- One canonical Scan finding produces one SARIF result.
- A deterministic opaque SARIF rule ID is derived from the stable Scan finding ID.
- Scan severity maps as follows:
  - `critical`, `high` -> `error`;
  - `medium`, `moderate` -> `warning`;
  - `low`, `info`, `informational` -> `note`;
  - `none` -> `none`;
  - unrecognized severities conservatively -> `warning`.
- Finding title, impact and recommendation form the result message and rule descriptions.
- Confidence, verification state, uncertainty, safe-verification guidance, evidence IDs and the canonical finding ID remain machine-readable result properties.

## Locations

GitHub code scanning requires at least one result location. Scan therefore exports a finding only when at least one referenced artifact is a repository-relative file artifact.

- The first referenced file is the primary SARIF location.
- Additional referenced files become `relatedLocations`; they do not create duplicate alerts.
- Paths are normalized to deterministic forward-slash relative URI references and URI-encoded.
- Absolute paths, traversal segments and non-file-only findings are rejected rather than silently dropped or rewritten to a misleading location.
- Scan does **not** invent a line number when the canonical evidence only establishes file-level location.
- Scan does **not** invent GitHub `primaryLocationLineHash` fingerprints when it has no line-level source hash. A future GitHub upload layer may let GitHub's supported upload tooling derive fingerprints.

This keeps source locations portable and avoids leaking owner-specific absolute paths.

## Validation

The implementation is tested against Scan regression fixtures and independently validated against the official OASIS SARIF 2.1.0 JSON schema. GitHub code scanning currently consumes the SARIF 2.1.0 subset and prefers repository-relative artifact URIs.

## Non-goals for this slice

- uploading SARIF to GitHub;
- adding a GitHub Action;
- PR comments or annotations;
- importing third-party SARIF/Semgrep/Trivy output;
- converting unknowns or failed coverage into alerts;
- synthesizing code regions from weak evidence;
- policy-as-code failure rules.

Those can build on this exporter in later v0.5 slices without changing the canonical Scan evidence model.
