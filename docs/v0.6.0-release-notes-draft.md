# Scan v0.6.0 release notes (draft)

Scan v0.6.0 advances Scan from a standalone inspection/reporting core toward a vendor-neutral evidence layer for trustworthy AI-assisted software inspection. The release focuses on portable evidence, exact provenance, honest unknowns, agent continuation, and measurable evaluation rather than adding a proprietary scanner engine.

This document is a draft for the release candidate. It does not mean v0.6.0 has been tagged, published on GitHub, or uploaded to PyPI.

## Highlights

### Vendor-neutral evidence federation

`scan import-evidence` imports bounded data-only results from specialist tools without loading or executing plugins. Imported results are bound to the exact Scan snapshot and canonical artifact content identity. The importer preserves producer/adapter/source provenance, retains unmappable results as unknowns, rejects stale artifact-byte bindings, and never treats a specialist tool's silence as a whole-project clearance.

### Observed test/runtime evidence

`scan import-observed` imports receipts from already-authorized external test/runtime systems. Scan records execution and authorization provenance while explicitly distinguishing external execution from Scan's own behavior. Authorization attestations remain `verified_by_scan=false`; import itself executes no target code and uses no network. Passing observations create bounded controls only for the declared case and cannot establish whole-project completeness.

### Deterministic agent handoff

`scan handoff` creates a bounded, digest-bound projection for another agent or session. It carries exact state/snapshot identity, findings, controls, unknowns, checks, actions, continuation context, and referenced evidence metadata while excluding source bytes and raw evidence-result payloads. Truncation is explicit rather than silently presented as complete.

### Portable Inspection Bundle v1

`scan-bundle create` packages canonical `state.json`, its deterministic default `handoff.json`, and a verified manifest into a constrained deterministic ZIP. `scan-bundle verify` checks archive metadata, member digests/sizes, canonical state, rebuilt handoff equality, coverage/readiness metadata, and exact state/snapshot identity without executing target code or using network access.

### Required AI-agent contribution receipts

The Scan skill now instructs every capable AI agent to create a privacy-safe post-run contribution receipt containing at least one actually observed test/validation outcome. Agents use `--submit auto`: submission occurs automatically only when caller/host policy already authorizes it and credentials are available; otherwise the receipt is queued locally. Authorized sessions retry a bounded outbox before finishing. Agents must report `submitted`, `duplicate`, or `queued` accurately and must not include target source, raw state/evidence, credentials, private records, arbitrary logs, or absolute target paths.

### ScanBench 2.0 ground-truth evaluation

The public ScanBench 2 corpus now contains 26 representative projects and 209 independently stated conditions across positive defects, negative controls, required unknowns, and no-clearance conditions. The evaluator keeps detection recall, specificity, unknown honesty, false-clearance violations, evidence support, and reference integrity separate rather than producing a blended quality score.

Additional benchmark integrity tooling includes corpus validation, independent-review receipt verification, review campaigns, holdout precommit/reveal verification, baseline ledgers, metamorphic anti-gaming tests, artifact grounding, oracle-consistency checks, and a maturity evidence auditor.

The 26/209 public corpus satisfies the numeric corpus target only. It does not by itself prove independent review coverage, externally custodied holdouts, or real-world effectiveness maturity; those remain separate evidence dimensions.

## Trust-boundary and release hardening

v0.6 includes the previously merged P0 trust-boundary fixes: changed-scope Git inspection avoids target-controlled clean/process filters, GitHub Action project policy ignores target `.scan/config.toml` by default unless the workflow owner opts in, and fresh semantic evidence is bound to its referenced canonical artifact identity.

The release gates now build and test installed wheel/source artifacts, exercise evidence-layer commands on Linux, Windows and macOS, pin current Node 24 GitHub Actions by exact commit SHA, verify ScanBench packaging, and run a dedicated v0.6 installed-artifact acceptance flow.

## Compatibility and safety notes

- Current Scan state schema remains `1.4`; historical validation compatibility remains available for supported earlier schemas.
- Evidence federation and observed-evidence v1 require Scan state schema 1.4.
- Inspection Bundle v1 is data-only and contains no executable plugin payloads.
- A bundle can contain redacted target-derived semantic text already present in canonical Scan state; sharing it requires the same privacy judgment as sharing the state/report.
- Scan still does not claim that static inspection proves runtime safety, that a passing specialist result clears uninspected behavior, or that benchmark corpus size equals product effectiveness.
