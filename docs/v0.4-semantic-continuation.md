# Scan v0.4 semantic MCP continuation

Status: **development slice; not a v0.4 release approval**

This slice lets a compatible MCP host continue from Scan's deterministic inventory into a validated semantic Scan workspace. The workspace is in memory, bound to one project snapshot, and deliberately does not authorize target execution, project modification, or network activity by Scan.

## Why this exists

Scan Core can deterministically answer questions such as:

- what artifacts exist;
- which bytes were hashed;
- whether a snapshot changed;
- what privacy/redaction boundary was applied;
- which check categories remain unassessed.

Those facts are necessary but not sufficient for architecture, correctness, security, usability, release-readiness, or other semantic judgments. The semantic MCP layer gives an agent a structured place to record those judgments without pretending the deterministic Core produced them.

## One snapshot, one workspace

The semantic workspace starts from a valid Scan 1.4 **deep** snapshot and records its snapshot digest.

Before every semantic mutation, Scan computes the current deep snapshot again. If the project bytes or paths have changed, further semantic writes are rejected as `stale` until the host explicitly calls:

```text
scan_semantic_reset
```

Reset discards the in-memory semantic work and seeds a new workspace from the current snapshot. It does not alter project files.

This prevents one semantic report from silently mixing evidence collected from different project states.

## Evidence authoring boundary

`scan_semantic_add_evidence` does not accept an arbitrary source digest from the model. Scan resolves the selected artifact from the canonical inventory, safely re-reads its current bytes, and requires the SHA-256 digest to match the workspace snapshot.

For this slice, semantic text evidence is accepted only when the artifact:

- is a regular file;
- has a complete SHA-256 content identity;
- is at most 1,000,000 bytes;
- is not a path-redacted or fully omitted sensitive artifact;
- is safely readable without following an unsafe link/reparse boundary;
- contains no NUL byte;
- is valid UTF-8;
- still matches the snapshot digest.

The evidence record's `source_digest` is supplied by Scan, not by the agent.

## Static semantic claims only

This slice intentionally permits only these evidence kinds:

```text
static
inferred
unverified
```

It rejects `observed` evidence and observed/runtime verification states. The semantic workspace therefore cannot turn static source reading into a claim that tests ran, a service worked, a deployment succeeded, or runtime behavior was observed.

Runtime verification remains a separate future/authorized operation.

## Producer identity

MCP-authored semantic evidence records whether the producer is:

```text
local-model
remote-model
```

The producer name and version are explicit evidence metadata. This keeps model-authored interpretation separate from deterministic Scan Core evidence.

## Semantic tools

The installed Scan MCP application exposes the deterministic Core tools plus these semantic tools:

### `scan_semantic_status`

Reports workspace freshness, snapshot identity, state digest, counts, check completion, and the no-write/no-execution/no-network boundary.

### `scan_semantic_reset`

Discards in-memory semantic work and starts again from the current deep Scan snapshot.

### `scan_semantic_add_component`

Adds a semantic architecture/component record linked to existing artifacts/evidence.

### `scan_semantic_add_evidence`

Adds one fresh evidence record after Scan rechecks the artifact bytes against the workspace snapshot.

### `scan_semantic_add_relationship`

Adds an evidence-linked static/inferred relationship between artifact/component IDs.

### `scan_semantic_add_finding`

Adds an evidence-linked finding with explicit impact, severity, confidence, uncertainty, recommendation, and safe verification path.

### `scan_semantic_add_unknown`

Records an unanswered question rather than converting missing evidence into a clean result.

### `scan_semantic_assess_check`

Updates one of Scan's required check categories. `assessed` and `partial` states require substantive evidence.

### `scan_semantic_mark_artifact_analyzed`

Marks an artifact `analyzed` only when direct substantive evidence is attached to that same artifact.

### `scan_semantic_finalize`

Updates summary/continuation fields and revalidates the canonical state. Claiming `analysis_complete=true` still has to satisfy Scan's existing validator rules.

### `scan_semantic_state`

Returns the validated in-memory Scan 1.4 semantic state plus its state digest.

## Semantic resources

Two read-only MCP resources make the completed workspace portable without writing into the target:

```text
scan://semantic/state
scan://semantic/report
```

`scan://semantic/state` returns deterministic canonical JSON.

`scan://semantic/report` renders that validated state through Scan's existing self-contained HTML renderer. Returning the HTML to the MCP host is not a project-file write. A host may save it somewhere else only according to the user's instructions and that host's own permissions.

## Transactional mutations

Semantic tool mutations are transactional. Before a mutation, Scan keeps an in-memory copy of the current semantic state. If the requested record fails builder or validator rules, the mutation is rolled back and the previously valid workspace remains intact.

This prevents one invalid model response from poisoning the rest of the semantic session.

## What does not change

The deterministic Core remains the authority for inventory, snapshot, privacy, baseline/reuse, and validation rules.

This slice does **not**:

- execute target code;
- run tests/builds automatically;
- perform network egress in the Scan process;
- change files in the inspected project;
- automatically save a semantic state/report to disk;
- accept arbitrary model-supplied artifact digests;
- allow observed/runtime evidence;
- remove unknowns merely because an agent produced prose;
- make the connected AI host itself offline.

The host/model remains a separate trust boundary and may transmit MCP tool inputs/outputs according to its own architecture, settings, and policy.

## Acceptance gates

This slice is ready to merge only when:

1. the base package remains usable without MCP installed;
2. a built wheel with `[mcp]` exposes the full deterministic + semantic tool surface;
3. the installed `scan-mcp config` launcher targets the full MCP application;
4. semantic evidence is digest-bound to the current Scan snapshot;
5. stale project bytes block semantic mutation until explicit reset;
6. observed/runtime claims are rejected;
7. binary/non-UTF-8 semantic text evidence is rejected;
8. invalid semantic mutations roll back cleanly;
9. exported semantic state passes the existing Scan 1.4 validator;
10. the semantic report resource is self-contained and renders from validated state;
11. a semantic session creates no `.scan` directory or other target output;
12. existing Core, ScanBench, browser/report, compatibility, and native-platform gates remain green;
13. source/control files remain UTF-8 without BOM.

## Current publication boundary

No v0.4 version bump, tag, GitHub Release, or PyPI publication is part of this slice. Until a separately approved v0.4 release, `scan-skill==0.3.1` remains the published package.
