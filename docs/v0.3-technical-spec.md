# Scan v0.3 Technical Specification

Status: **Proposed implementation contract; owner approval pending**
Target release: **v0.3 (publication, tagging and package publishing remain separate owner-approved actions)**
Compatibility baseline: **Scan Core v0.2 / Scan state 1.3**
Primary principle: **A second Scan must be more useful than the first without making old evidence look fresher than it is.**

This specification defines Scan v0.3 as the **habit release**. v0.2 established deterministic local inventory, canonical state, privacy/redaction, static HTML rendering, validation and ScanBench v1. v0.3 adds the minimum capabilities required to make repeated scanning meaningfully better than one-shot scanning: baselines, deterministic diffs, evidence freshness/reuse, Git-aware change context, installation diagnostics and cross-platform release hardening.

Normative words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** describe release requirements.

## 1. Release goals

v0.3 MUST provide:

1. Automatic local baseline discovery for repeated scans without requiring a hosted service.
2. Deterministic state-to-state comparison for artifacts, findings and unknowns.
3. Evidence freshness and safe reuse semantics that never upgrade historical inspection depth.
4. A `scan compare` command for comparing two existing Scan states without rescanning.
5. Git-aware changed-scope context through an explicit `--changed-since REF` option while preserving whole-project inventory.
6. A `scan doctor` command that diagnoses installation, package assets, project access and optional Git integration without network access.
7. Scan state schema 1.4 as an additive evolution of 1.3.
8. HTML and terminal summaries that make the second scan immediately useful by showing the baseline delta.
9. Native Windows and macOS CI release gates in addition to Linux.
10. Release/install hardening so a built v0.3 artifact can be installed cleanly as a standalone CLI.
11. Updated agent-skill guidance so AI hosts consume baseline, freshness and change-scope evidence without overstating what was rechecked.

### 1.1 Product outcome

The default repeated workflow should become:

```text
first scan
  -> establish current canonical state

change project
  -> scan again
  -> compare against previous valid local state
  -> show what changed
  -> reuse only compatible evidence
  -> preserve unknowns and limitations honestly
```

The intended user experience is that the **second Scan is materially more useful than the first**.

### 1.2 Non-goals

The following are explicitly out of v0.3:

- SARIF export;
- GitHub Action or GitHub App;
- pull-request comments or annotations;
- Semgrep, CodeQL, Trivy or other external-scanner adapters;
- public ScanBench Arena;
- ScanBench AI-Slop, Agent-Honesty or other new benchmark packs;
- universal quality or security scores;
- Scan Cards or public badges beyond existing CI status;
- policy-as-code enforcement;
- MCP server;
- VS Code extension;
- local or remote model-provider execution;
- controlled remote transmission;
- hosted history or team dashboard;
- browser scanning;
- autonomous target execution;
- automatic remediation;
- automatic rename inference;
- changed-files-only inventory.

These remain later-release work. v0.3 MUST leave clean extension points for them without shipping partial versions.

## 2. Compatibility and versioning

v0.3 introduces two version axes:

- **software version**: Scan v0.3.x;
- **canonical state contract**: Scan state `schema_version: "1.4"`.

The validator MUST preserve historical support for 1.2 and 1.3.

```text
Scan 1.2 historical report -> validate as 1.2
Scan 1.3 state/report      -> validate as 1.3
Scan 1.4 state/report      -> validate as 1.4
```

A 1.2 or 1.3 file MUST NOT be silently rewritten or relabeled as 1.4.

v0.3 implementation branches MAY use development versions such as `0.3.0.dev1`, `0.3.0.dev2`, and so on. Creating a public tag, release or package publication is a separate owner-approved action.

### 2.1 Baseline compatibility

Automatic or explicit baselines MUST be canonical Scan state 1.3 or 1.4.

Historical 1.2 reports remain valid historical inputs for validation and rendering where already supported, but MUST NOT be used as v0.3 evidence-reuse baselines because they do not contain the complete 1.3 producer/privacy/provenance contract required by the reuse rules.

`scan compare` MUST accept 1.3 and 1.4 canonical JSON states.

## 5. Default repeated-scan behavior

The default state output remains `.scan/state.json` unless overridden.

Before scanning, Scan MUST resolve the baseline **before** replacing the current output state.

Default baseline mode is `auto`.

### 5.1 First scan

If the configured state output does not already exist:

```text
baseline.mode   = auto
baseline.status = not_found
```

The scan proceeds normally and writes the current state atomically.

### 5.2 Subsequent scan

If the configured state output already exists and validates as compatible state 1.3 or 1.4:

1. load that state as the automatic baseline;
2. perform a fresh current inventory and snapshot;
3. compare current state against the loaded baseline;
4. evaluate evidence reuse under the rules in this specification;
5. build and validate current state 1.4;
6. atomically replace the state output only after the new state validates;
7. render HTML from the new state.

The prior state does not need a duplicate history copy in v0.3. The existing state file is the automatic baseline until a new valid state replaces it.

### 5.3 Failed automatic baseline

If an automatic baseline exists but cannot be parsed, validated or used compatibly:

- the scan MUST NOT silently claim a comparison;
- the scan SHOULD warn and continue as a fresh full scan;
- `baseline.status` MUST record the reason as `invalid` or `incompatible`;
- evidence MUST NOT be reused from that baseline.

### 5.4 Failed explicit baseline

If the user explicitly supplies a baseline path and it is missing, invalid or incompatible, Scan MUST fail before replacing the current output state.

Use exit code `5` when the explicit baseline exists but fails Scan validation, and exit code `3` when the source path cannot be accessed.

## 6. CLI contract

The existing v0.2 commands remain supported.

### 6.1 Primary scan command

```bash
scan PATH [options]
```

v0.3 adds:

```text
--baseline VALUE          auto | none | PATH; default auto
--no-reuse                compare against baseline but do not reuse prior evidence
--changed-since REF       add local Git change context relative to REF
```

Examples:

```bash
scan . --offline
scan . --baseline none
scan . --baseline auto
scan . --baseline ./previous.scan.json
scan . --baseline auto --no-reuse
scan . --changed-since origin/main
```

`--baseline auto` MUST resolve only local state already present at the configured state output path. It MUST NOT search the network, GitHub, remote branches or arbitrary filesystem locations.

`--baseline PATH` MUST resolve only the exact user-supplied local file.

`--changed-since REF` MUST NOT reduce inventory coverage. It adds change context only.

There MUST NOT be a v0.3 `--changed-only` option.

### 6.2 Compare command

```bash
scan compare OLD_STATE NEW_STATE [--json]
```

Examples:

```bash
scan compare old.scan.json new.scan.json
scan compare old.scan.json new.scan.json --json
```

`scan compare`:

- MUST NOT rescan either project;
- MUST NOT execute target code;
- MUST NOT use the network;
- MUST validate both input states before comparison;
- MUST produce the same logical result for the same two input states;
- MUST compare 1.3 and 1.4 states through a normalized in-memory comparison view without rewriting the source files.

Human output SHOULD be concise. `--json` MUST emit a machine-readable comparison record to stdout.

### 6.3 Doctor command

```bash
scan doctor [PATH] [--json]
```

`PATH` defaults to `.`.

`scan doctor` MUST check at least:

- supported Python runtime;
- installed Scan version;
- bundled state schemas 1.2, 1.3 and 1.4;
- packaged report shell/assets required for normal operation;
- packaged ScanBench manifest/fixtures required by the installed wheel;
- target path existence/readability;
- ability to create the configured `.scan` output directory or an equivalent temporary probe without leaving a stale artifact;
- optional Git executable availability;
- whether the target is inside a local Git worktree when Git-dependent features are requested later.

Doctor check states are:

```text
pass
warn
fail
```

Git absence is a warning for ordinary Scan use because Git is optional. Missing required package assets is a failure.

Doctor MUST NOT contact package registries, GitHub or any other network service.

### 6.4 Schema command

```bash
scan schema --version 1.2
scan schema --version 1.3
scan schema --version 1.4
```

### 6.5 Existing exit codes

v0.3 MUST preserve the existing stable exit-code contract:

| Code | Meaning |
|---:|---|
| 0 | requested operation completed successfully |
| 2 | command/configuration/install diagnostic failure |
| 3 | source path/access failure |
| 4 | scan completed but declared coverage threshold was not met |
| 5 | validation failed |
| 6 | privacy/redaction policy blocked the requested operation |
| 7 | resource/safety limit reached |
| 10 | unexpected internal Scan error |

No new exit code is required for v0.3.

### 6.6 Project configuration additions

The existing precedence remains:

```text
CLI arguments > .scan/config.toml > built-in defaults
```

v0.3 adds an optional baseline section:

```toml
[baseline]
mode = "auto"              # auto | none
reuse = true
max_state_bytes = 64000000
```

Rules:

- `mode` defaults to `auto`.
- `reuse` defaults to `true` and uses the strict compatibility rules in this specification.
- `max_state_bytes` defaults to 64,000,000 bytes.
- An explicit baseline file path is CLI-only in v0.3 and MUST NOT be persisted automatically into project config.
- `--baseline none` overrides `mode = "auto"`.
- `--baseline PATH` selects explicit mode for that invocation.
- `--no-reuse` overrides `reuse = true` for that invocation.

The resolved configuration digest MUST include baseline mode, reuse policy and baseline read ceiling. It MUST NOT include an absolute baseline source path. The actual baseline identity belongs in `baseline.source_state_digest` and `baseline.source_snapshot_digest`.

## 7. Baseline identity and state digest

v0.3 MUST define a canonical state digest helper.

```text
state_digest = sha256(canonical UTF-8 JSON bytes of the state as stored)
```

The digest identifies the exact state record, including its run metadata. It is distinct from the project snapshot digest, which identifies the normalized inspected project snapshot.

A baseline record MUST preserve both:

```text
source_state_digest
source_snapshot_digest
```

This prevents a caller from confusing “same project bytes” with “same inspection record.”

## 8. Deterministic artifact comparison

Artifact matching is by existing Scan artifact ID, which is path-derived.

For each baseline/current pair:

```text
added      current ID absent from baseline
removed    baseline ID absent from current
unchanged  same ID and same comparison fingerprint
changed    same ID but comparison fingerprint differs
```

The artifact comparison fingerprint MUST be derived from stable, non-temporal fields including at least:

```text
artifact id
path_kind
content_identity
size_bytes
status
redaction_state
```

Run timestamps and evidence timestamps MUST NOT affect artifact delta classification.

### 8.1 Rename behavior

v0.3 MUST NOT silently infer renames.

If `old/path.py` disappears and `new/path.py` appears with identical bytes, the deterministic result is:

```text
old/path.py -> removed
new/path.py -> added
```

Future versions MAY add an advisory rename-candidate layer, but path identity remains authoritative.

## 9. Finding and unknown comparison

Findings and unknowns are compared by their stable IDs.

For findings, state 1.4 delta MUST expose:

```text
new
resolved
persisting
modified
```

`persisting` contains IDs present in both states. `modified` is a subset of `persisting` whose normalized non-temporal record changed.

Unknowns MUST expose the same categories:

```text
new
resolved
persisting
modified
```

In delta terminology, `resolved` means only that the prior record ID is absent from the current valid state. Scan MUST NOT translate that category into “fixed”, “remediated” or “verified resolved” unless current evidence supports that stronger claim. If a related artifact was removed, the artifact removal remains visible separately.

## 10. Evidence freshness and reuse

A baseline is not a trust cache.

Fresh current inventory/provenance evidence MUST always be regenerated because the current snapshot must be established independently.

Higher-level prior evidence MAY be reused only when all required compatibility conditions pass.

### 10.1 Required reuse conditions

The default reuse decision MUST require:

```text
same current artifact ID
AND same source/content digest
AND compatible producer identity
AND compatible producer version under exact-match default policy
AND compatible check identity/definition
AND previous evidence actually existed
AND previous evidence was not blocked or unsupported
AND current privacy/redaction policy can represent it safely
AND evidence class is eligible for reuse
```

Runtime verification evidence MUST NOT be automatically reused in v0.3.

Evidence whose correctness depends on environment, deployment state, live service state, time-sensitive dependencies or runtime execution MUST be treated as non-reusable unless a future version adds an explicit freshness policy for that evidence class.

### 10.2 Reuse must not upgrade depth

Reusing evidence MUST NOT change historical depth upward.

Examples:

```text
previous partial -> reused partial
previous static  -> reused static
previous unknown -> remains unknown unless fresh evidence resolves it
```

Matching bytes alone MUST NOT turn `content_read` into `analyzed`, `partial` into `assessed`, or `static` into `runtime_verified`.

### 10.3 Reused evidence metadata

A reused evidence record in state 1.4 MUST include:

```json
{
  "freshness": {
    "status": "verified_reuse",
    "source_state_digest": "sha256:...",
    "source_evidence_id": "evidence:...",
    "original_observed_at": "RFC3339 timestamp",
    "reused_at": "RFC3339 timestamp",
    "reuse_reason": "identical_content_identity"
  }
}
```

Fresh evidence MUST include:

```json
{
  "freshness": {
    "status": "fresh",
    "source_state_digest": null,
    "source_evidence_id": null,
    "original_observed_at": "RFC3339 timestamp",
    "reused_at": null,
    "reuse_reason": null
  }
}
```

Allowed v0.3 `freshness.status` values are:

```text
fresh
verified_reuse
```

Stale or rejected baseline evidence MUST NOT be copied into the current live evidence collection merely to explain why it was rejected. Reuse diagnostics belong in the baseline/reuse summary.

### 10.4 Reuse diagnostics

State 1.4 MUST count at least:

```text
fresh_evidence_count
reused_evidence_count
rejected_reuse_count
```

Rejected reuse SHOULD expose machine-readable reason counts without copying unsafe baseline content.

## 11. Git-aware changed scope

`--changed-since REF` adds local Git context to a Scan; it does not replace baseline comparison.

Implementation MAY invoke the local `git` executable with argument arrays and without a shell.

Scan MUST NOT:

- fetch a missing ref;
- contact a remote;
- execute Git hooks;
- execute target code;
- treat Git output as proof that untracked or ignored filesystem artifacts do not exist.

The Git command path MUST be treated as an optional local integration and recorded in tool provenance when used.

### 11.1 Git change categories

The state SHOULD record local Git change context for:

```text
added
modified
deleted
renamed
copied
untracked
```

Git rename/copy information is advisory source-control context only. It MUST NOT alter Scan artifact identity or deterministic baseline artifact categories.

### 11.2 Whole-project coverage remains authoritative

Even with `--changed-since`:

- inventory still covers the declared project scope;
- hidden/generated/vendor treatment remains governed by Scan configuration;
- changed paths are a prioritization/context signal;
- coverage claims remain whole-project claims only where actual whole-project evidence supports them.

## 12. Canonical Scan state 1.4

State 1.4 is additive to 1.3.

It MUST retain all existing 1.3 top-level collections and add baseline/delta information.

### 12.1 Baseline object

Every first-party v0.3 state MUST include:

```json
{
  "baseline": {
    "mode": "auto",
    "status": "used",
    "source_schema_version": "1.3",
    "source_state_digest": "sha256:...",
    "source_snapshot_digest": "sha256:...",
    "snapshot_relation": "changed",
    "reuse_enabled": true,
    "fresh_evidence_count": 100,
    "reused_evidence_count": 12,
    "rejected_reuse_count": 3,
    "rejected_reuse_reasons": {
      "changed_content": 2,
      "producer_version_mismatch": 1
    }
  }
}
```

Allowed `baseline.status` values:

```text
used
not_found
disabled
invalid
incompatible
```

Allowed `snapshot_relation` values:

```text
same
changed
unknown
none
```

If no baseline is used, source digests and source schema version are null and `snapshot_relation` is `none` or `unknown` as appropriate.

### 12.2 Delta object

Every first-party v0.3 state MUST include:

```json
{
  "delta": {
    "available": true,
    "artifacts": {
      "added": [],
      "changed": [],
      "removed": [],
      "unchanged": []
    },
    "findings": {
      "new": [],
      "resolved": [],
      "persisting": [],
      "modified": []
    },
    "unknowns": {
      "new": [],
      "resolved": [],
      "persisting": [],
      "modified": []
    }
  }
}
```

When no valid baseline is available:

```text
delta.available = false
```

and all category arrays MUST be empty.

### 12.3 Optional Git change context

When `--changed-since` is used, state 1.4 MUST record the request and result under an extension namespace rather than redefining artifact delta semantics.

Recommended shape:

```json
{
  "extensions": {
    "git_change_scope": {
      "base_ref": "origin/main",
      "head_ref": "HEAD",
      "git_version": "git version ...",
      "added": [],
      "modified": [],
      "deleted": [],
      "renamed": [],
      "copied": [],
      "untracked": []
    }
  }
}
```

## 13. Comparison determinism

For the same two input state files, `compare_states(old, new)` MUST produce the same logical comparison output regardless of:

- input object key ordering;
- operating system;
- current wall-clock time;
- current working directory;
- discovery order.

The comparison record MUST derive any comparison timestamp from existing input state metadata, not from a fresh wall-clock timestamp.

## 14. Privacy requirements for baselines and diffs

The current privacy policy always wins.

v0.3 MUST NOT reintroduce content or locators that were hidden by the current redaction/sensitive-path policy merely because an older baseline was less restrictive.

When prior evidence is reused:

- its text fields MUST pass current redaction before inclusion;
- sensitive path aliases MUST be normalized to the current safe representation;
- deleted sensitive artifacts MUST be represented by safe identity/provenance metadata only;
- baseline source paths MUST not leak absolute local paths into canonical state;
- terminal diff output MUST not print raw secret values.

An invalid or privacy-incompatible baseline MUST degrade to no reuse rather than weaken current privacy.

## 15. HTML report behavior

The HTML report remains a presentation of validated canonical state.

For state 1.4 with an available baseline, the report MUST add a concise **Since baseline** section containing at least:

```text
artifacts added
artifacts changed
artifacts removed
new findings
resolved findings
new unknowns
resolved unknowns
fresh evidence count
reused evidence count
```

The report MUST distinguish current fresh analysis from reused evidence visibly.

The renderer MUST NOT recompute delta categories independently. Visible counts must come from canonical state and be validator-checkable.

Historical 1.2 and 1.3 reports remain renderable/valid according to their existing contracts and do not gain fabricated baseline data.

## 16. Terminal UX

The default command output SHOULD remain compact.

First scan example:

```text

Inventory    428 artifacts
Snapshot     sha256:...
Privacy      offline
Baseline     none (first scan)

Report       .scan/report.html
State        .scan/state.json
```

Repeated scan example:

```text

  + 3 artifacts
  ~ 8 changed
  - 1 removed

  + 1 new finding
  ✓ 2 findings resolved
  ? 1 new unknown

Evidence
  391 fresh
   24 safely reused

State        .scan/state.json
```

No universal Scan score is introduced.

## 17. Agent-skill integration

`SKILL.md` MUST be updated in the v0.3 implementation line to teach compatible AI hosts the following rules:

1. Consume `delta` before rereading the entire state when the user asks what changed.
2. Treat Git changed scope as prioritization context, not proof of project completeness.
3. Reused evidence retains its original depth and limitations.
4. Do not say an unchanged artifact was freshly semantically reviewed when its evidence was reused.
5. Prefer fresh analysis for changed artifacts and connected high-risk areas.
6. Preserve explicit unknowns that were not actually resolved.
7. Never treat baseline disappearance of a finding as proof of runtime remediation without supporting current evidence.

The skill remains agent-neutral and MUST NOT hard-code a model provider.

## 18. `scan doctor` release contract

Doctor output MUST be both human-readable and machine-readable with `--json`.

Machine-readable shape SHOULD include:

```json
{
  "scan_version": "0.3.0",
  "overall": "pass",
  "checks": [
    {
      "id": "python-version",
      "status": "pass",
      "message": "Python 3.12 supported"
    }
  ]
}
```

Doctor MUST return nonzero only for actual required failures or invalid source access, not for optional Git absence.

Doctor MUST clean up any temporary probe it creates.

## 19. Distribution and installation hardening

v0.3 implementation MUST be buildable as both wheel and source distribution from a clean checkout.

The Python distribution name remains `scan-skill` for the v0.3 implementation contract. Renaming the package is outside this release unless separately approved before implementation begins.

The console command remains:

```text
scan
```

Release documentation MAY describe commands such as:

```bash
pipx install scan-skill
uv tool install scan-skill
```

only after the corresponding package is actually published. Until then, documentation MUST clearly distinguish source/GitHub installation from registry installation.

v0.3 implementation work MUST NOT itself publish to PyPI, create a public release, create a tag or announce the project without separate owner approval.

## 20. Cross-platform CI

v0.3 release gates MUST include native:

```text
Ubuntu
Windows
macOS
```

At minimum:

- full core tests on Python 3.12 for all three operating systems;
- ScanBench v1 on Python 3.12 for all three operating systems;
- Python 3.11 and 3.13 compatibility jobs on Ubuntu;
- package build/install smoke test from the built wheel;
- installed `scan` entrypoint smoke test;
- baseline/diff tests using platform-appropriate paths;
- Unicode/space-containing path tests;
- symlink tests where the runner supports them, with explicit skip reasons where platform policy prevents creation rather than silently dropping coverage.

Release CI MUST keep Windows path semantics and case behavior visible rather than normalizing failures away.

## 21. Public Python API

v0.3 SHOULD add a small typed comparison surface without exposing every implementation helper.

Required public functions:

```python
def compare_states(previous: Mapping[str, Any], current: Mapping[str, Any]) -> Comparison: ...
def evaluate_reuse(previous_evidence: Mapping[str, Any], current_artifact: Mapping[str, Any], policy: ReusePolicy) -> ReuseDecision: ...
def state_digest(state: Mapping[str, Any]) -> str: ...
def run_doctor(path: Path) -> DoctorResult: ...
```

Baseline path resolution and Git subprocess details MAY remain private implementation APIs.

## 22. Migration rules

v0.3 has no destructive migration command.

Migration is **read old, emit new**:

```text
1.3 baseline --validate--> in-memory normalized comparison view
current scan -------------> native 1.4 state
```

Rules:

1. 1.3 source files are never modified in place.
2. Missing 1.4-only baseline/delta fields in a 1.3 baseline are treated as absent historical metadata, not errors.
3. Evidence reuse from 1.3 is allowed only when all v0.3 compatibility rules can be established from fields that actually exist.
4. If compatibility cannot be established, evidence is not reused.
5. 1.2 remains validation-only for this feature set.
6. 1.4 rendering must not require changing historical demo files.

## 23. Resource and safety limits

Comparison MUST be bounded.

The resolved `baseline.max_state_bytes` value defaults to **64,000,000 bytes**. Exceeding the ceiling returns exit code `7` for an explicit comparison/baseline operation and degrades automatic baseline use to unavailable with a clear warning during a normal scan.

Comparison should be approximately linear in the number of state records by indexing IDs rather than repeatedly scanning lists.

No baseline feature may cause target code execution.

## 24. Required v0.3 test matrix

The implementation MUST test at least the following.

### 24.1 Baseline resolution

```text
first run -> no baseline
second run -> prior valid state used automatically
--baseline none -> no comparison
explicit valid 1.3 baseline -> accepted
explicit valid 1.4 baseline -> accepted
explicit invalid baseline -> fails before overwrite
auto invalid baseline -> warns and continues without reuse
failed new-state validation -> old state remains intact
```

### 24.2 Artifact comparison

```text
unchanged path + unchanged bytes -> unchanged
same path + changed bytes -> changed
new path -> added
removed path -> removed
rename with identical bytes -> removed + added
input ordering changes -> same delta
```

### 24.3 Finding/unknown comparison

```text
new IDs classified new
missing old IDs classified resolved
same IDs classified persisting
same ID with changed normalized record classified modified
timestamps alone do not classify modified
resolved delta label is not presented as verified remediation without evidence
```

### 24.4 Evidence reuse

```text
identical artifact + same producer/version/check -> reusable
changed bytes -> reject reuse
producer version mismatch -> reject reuse
missing source digest -> reject reuse
runtime evidence -> reject automatic reuse
partial historical evidence remains partial
reused evidence preserves original_observed_at
current strict redaction cannot leak less-redacted baseline text
--no-reuse -> zero reused evidence
```

### 24.5 Git change scope

```text
valid local ref -> change context recorded
missing ref -> explicit command error
no Git installed -> ordinary scan still works
--changed-since without Git -> clear failure for requested feature
untracked file remains discoverable by Scan inventory
Git rename does not rewrite Scan artifact identity
no Git network operation occurs
```

### 24.6 Doctor

```text
healthy installed package -> pass
missing optional Git -> warn
missing bundled schema -> fail
unreadable target path -> source error
JSON output stable and typed
temporary probes cleaned up
```

### 24.7 Rendering and validation

```text
1.2 historical validation still passes
1.3 validation still passes
1.4 state validates
1.4 HTML embedded state validates
visible delta counts match canonical state
reused evidence is visibly distinguished
invalid delta references are rejected
```

### 24.8 Cross-platform

```text
spaces in paths
Unicode filenames
Windows separators normalized safely
macOS/Linux symlink behavior
case-sensitive/case-insensitive path edge cases documented and tested where applicable
```

## 26. Per-slice merge gate

Every implementation PR MUST satisfy:

```text
existing frozen 1.2 validator tests pass
existing 1.3 tests pass
new slice tests pass
ScanBench v1 mandatory fixtures pass
git diff --check passes
package compile/import smoke passes
no target code executed by tests unless the fixture explicitly tests Scan itself
no network required for core tests
no secret fixture value leaks into generated state/report/test logs
```

A slice that changes user-visible CLI behavior MUST also test the installed console entrypoint, not only direct Python imports.

## 27. Final v0.3 release acceptance gate

From a clean checkout and a built/installed package, the release candidate MUST support:

```bash
scan . --offline
scan . --offline
scan validate .scan/state.json
scan validate .scan/report.html
scan schema --version 1.4
scan doctor .
scan bench
```

The second `scan . --offline` MUST use the first state as its automatic baseline and produce a valid baseline/delta record.

Fixture-based gates MUST additionally prove:

```bash
scan compare tests/fixtures/baseline/old-state.json tests/fixtures/baseline/new-state.json --json
scan tests/fixtures/git-scope/project --changed-since HEAD~1 --no-reuse
```

where the Git fixture is created safely by the test harness and does not require a network remote.

Release completion requires:

- 1.2 historical compatibility preserved;
- 1.3 compatibility preserved;
- 1.4 JSON and HTML validation passing;
- deterministic baseline/delta semantics;
- no rename overclaim;
- no evidence-depth upgrade through reuse;
- no runtime evidence auto-reuse;
- current privacy policy wins over baseline data;
- auto-baseline failure degrades honestly;
- explicit invalid baseline fails before overwrite;
- Git integration remains local/no-network;
- doctor works from the installed package;
- ScanBench v1 still passes;
- Windows, macOS and Linux required CI gates pass;
- wheel installation exposes a functioning `scan` entrypoint.

## 28. README/onboarding requirements

v0.3 documentation SHOULD optimize first value before historical proof.

README ordering SHOULD become:

```text
what Scan is
-> install/use current Scan
-> scan . --offline
-> second-scan delta
-> why the evidence is trustworthy
-> historical synthetic demo
-> deeper contracts/ScanBench
```

The historical demo remains valuable but SHOULD NOT be the first activation path for a new user.

The primary message remains:

> **Know what your AI actually inspected.**

A secondary explanatory message MAY use:

> **Every AI says it read your project. Scan keeps the receipts.**

Neither line is a security guarantee.

## 30. Definition of done

Scan v0.3 is done when a user can scan a project twice and reliably answer:

```text
What changed?
What stayed the same?
Which evidence is fresh?
Which evidence was safely reused?
Which evidence could not be reused?
What remains unknown?
```

without Scan:

- executing target code;
- requiring a cloud service;
- contacting a Git remote;
- weakening current privacy;
- treating unchanged bytes as deeper inspection;
- hiding incomplete coverage behind a score.

That is the v0.3 contract.
