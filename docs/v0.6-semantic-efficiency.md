# Scan v0.6 semantic-efficiency slice

Status: **development slice; not a v0.6 release approval**

## Purpose

This slice reduces avoidable AI/context work without weakening Scan's evidence or whole-project coverage rules.

It deliberately does **not** introduce fixed LLM token caps, a dependency graph, an embeddings index, a policy language, or automatic target-code execution. The first goal is simpler: consume trustworthy change/reuse context before asking an agent to reread source.

## Semantic-effort order

For a repeat or change-focused inspection, agents should prefer this order:

1. canonical baseline `delta`, when available;
2. verified reusable semantic evidence for byte-identical artifacts;
3. `extensions.git_change_scope.priority_paths`, when `--changed-since` was requested;
4. fresh inspection of those changed paths and any consequential connections established from evidence;
5. the remaining in-scope first-party artifacts required by the selected coverage mode.

`deep` remains Scan's whole-project first-party mode. Prioritization changes order; it does not convert Deep into diff-only review. If an actual resource/context/access boundary prevents completion, the result remains explicitly partial.

## Deterministic priority paths

`GitChangeScope` now exposes `priority_paths`, a sorted union of current paths that are:

- added;
- modified;
- untracked;
- rename destinations; or
- copy destinations.

Deleted paths remain in the ordinary `deleted` field because there are no current bytes to inspect.

The field is emitted inside the existing `extensions.git_change_scope` object. Paths have already passed the same sensitive-path handling as the surrounding Git change scope.

Example:

```json
{
  "extensions": {
    "git_change_scope": {
      "modified": ["src/ledger.py"],
      "untracked": ["tests/test_ledger.py"],
      "priority_paths": ["src/ledger.py", "tests/test_ledger.py"]
    }
  }
}
```

## Evidence boundary

`priority_paths` is advisory ordering context only. It does not prove:

- that unchanged files are irrelevant;
- that a listed file affects any particular caller/callee;
- that related tests were identified;
- that semantic analysis occurred;
- that the project is complete or safe.

Any relationship beyond the direct Git change facts must come from separate evidence and keep its proper verification state.

## Why no numeric token budget yet

Model hosts expose different context windows, accounting semantics and tool-call behavior. A fixed value such as "Deep = 200k tokens" would be arbitrary until Scan measures real runs on representative repositories.

Instead, this slice removes obvious redundant work first. Later benchmarking can record host/model, scan mode, fresh vs reused evidence, semantic input/output usage when available, and finding/coverage outcomes. Numeric budgets should only be considered after those measurements show a stable useful policy.

## Non-goals

This slice does not add:

- call/import/dependency graph construction;
- AST support for multiple languages;
- automatic related-test discovery;
- AI-slop heuristics;
- dynamic UX/browser testing;
- OPA or another policy engine;
- automatic skipping of unchanged files when reusable evidence is unavailable;
- claims of a particular percentage token saving.

Those can be evaluated separately after this low-risk efficiency baseline is measured.

## Acceptance gates

1. `priority_paths` contains every current added/modified/untracked path and rename/copy destination exactly once.
2. Deleted paths are not added to `priority_paths` merely because they were deleted.
3. Sensitive-path-safe values remain safe; the helper never reopens or resolves paths.
4. Existing Git change categories remain unchanged.
5. The field stays advisory and does not alter canonical artifact status, evidence depth, check status or `analysis_complete`.
6. Coverage guidance explicitly preserves Deep's whole-project obligation and verified-reuse rules.
7. Tests cover deduplication, rename/copy destinations, deleted paths and redacted-safe values.
