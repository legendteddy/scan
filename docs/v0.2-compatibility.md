# Scan v0.2 Compatibility and Release Boundary

Scan v0.2 has two separate version axes:

- **software:** `0.2.x` development/release versions;
- **report state:** historical schema `1.2` and current standalone-core schema `1.3`.

## Supported Python

The packaged standalone core requires Python **3.11, 3.12 or 3.13**. CI keeps the main validation job on Python 3.12 and runs compatibility gates on 3.11 and 3.13.

The historical `scripts/validate_report.py` path remains stdlib-only and preserves the existing Scan 1.2 example/validator behavior.

## Report compatibility

- Scan 1.2 HTML remains a valid historical input.
- Scan 1.2 state is never silently relabeled or rendered as 1.3.
- Scan 1.3 JSON is the authoritative state emitted by the v0.2 standalone core.
- Scan 1.3 HTML is a self-contained presentation of validated canonical state and embeds exactly one inert `project-anatomy-state` JSON block.
- The 1.3 report validator additionally rejects executable scripts, external network resources and mechanically detectable visible-count drift.

`scan schema --version 1.2` and `scan schema --version 1.3` expose bundled structural JSON Schemas. Cross-reference, coverage, provenance, privacy and HTML-integrity rules remain enforced by the Scan validator because those constraints exceed ordinary JSON Schema structure checks.

## Configuration compatibility

Optional project configuration is read from `.scan/config.toml` using the Python standard library. Precedence is:

```text
CLI arguments > .scan/config.toml > built-in defaults
```

Unknown configuration sections/keys and invalid types fail closed as command/configuration errors. Resolved behavior-affecting values feed the canonical configuration digest. Configuration does not require credentials.

## ScanBench v1

The v0.2 release gate contains 12 mandatory synthetic fixtures and five independent benchmark dimensions:

```text
inventory completeness
state integrity
evidence correctness
privacy integrity
safety-boundary compliance
```

There is no blended overall quality score. `scan bench` returns nonzero if a mandatory expected assertion fails. The canonical fixture data is also shipped with the wheel so the benchmark can run outside the source checkout.

## Static-first safety boundary

The deterministic v0.2 core does not execute target scripts/tests/binaries, install target dependencies, evaluate inspected HTML/JavaScript, fetch URLs found in source, follow symlinks outside the declared root, or perform remote egress. `controlled-remote` is a recorded policy mode only; v0.2 has no remote provider adapter.

Archives are inventoried as files and are not expanded or executed by the core. Unsupported binary content can be hashed for identity but is not promoted to semantic analysis.

## Release boundary

Merging the v0.2 implementation does **not** by itself publish a package, create a GitHub Release, create a version tag, or promote the project publicly. Those are separate owner-approved release actions.
