# HTML state contract — 1.4

Embed one authoritative inert JSON block: `<script type="application/json" id="project-anatomy-state">…</script>`. Retain this stable ID despite the skill rename. No additional script blocks are permitted, including other JSON scripts. Serialize with a real JSON serializer, escaping `<`, `>` and `&` as JSON Unicode escapes; escape visible text independently. Do not use NaN, duplicate JSON keys or dangling ID references. Describe adaptive fields in `extensions`; do not substitute a legacy or custom schema. Old reports are historical input, not automatically compliant output.

Required objects and fields below are structural minimums. Use nonempty strings for substantive prose, arrays for lists/references, and globally unique IDs. Use empty lists when appropriate; explain absent checks in coverage/unknowns. Do not invent records to satisfy validation.

## Core objects

- `schema_version`: `1.4` for current reports. Historically accepted validation versions are `1.2` and `1.3`; preserve their original labels and evidence.
- `run`: `scan_id`, `scan_version`, `started_at`, `completed_at`, execution `mode`, `target_executed`, and `network_used`. Current core output also records `scan_mode` (`quick`, `deep`, or `forensic`) when available.
- `privacy`: `mode`, `redaction_level`, `redaction_count`, `sensitive_path_count`, `egress_performed`, and `egress_bytes`. Counts must reconcile with artifact/evidence redaction metadata.
- `provenance`: `root_identity`, `snapshot_digest`, `state_digest_algorithm`, `tool_versions`, and `configuration_digest`. Current Git-aware output may add bounded `git` provenance without hashing repository object storage in normal deep mode.
- `project`: `name`, `purpose`, `target_types` (strings), `source_locators` (strings), `snapshot` (identity/version and time object), `scope` (string), `exclusions` (strings), `critical_artifact_ids` (artifact references). Identify principal application/entry points or content. Explain in `extensions` when no critical artifacts can be identified.
- `summary`: `overview`, `operation`, `condition`, `strengths` (strings), `priorities` (strings), `readiness`, `evidence_ids`, `limitations`. Limit the verdict to the scope actually supported.
- `coverage`: `discovery_complete` and `analysis_complete` (booleans), `discovered_artifact_count` (integer), `counts_by_status` (status-to-count object), `limits` (strings), `sampling` (string), `methods` (strings), `checks_performed` and `checks_not_performed` (strings), `snapshot_consistency` (string), `sensitive_omissions` (strings), `counts_by_check_status` (status-to-count object), `checks_complete` (boolean). Check completeness is separate from artifact analysis completeness. Counts must reconcile to embedded artifact rows; count archive containers and members separately and explain granularity in extensions. Discovery completeness is relative to the declared scope, not proof of no external dependencies. Analysis completeness means every in-scope artifact has undergone its relevant semantic inspection; excluded, partial, unreadable and metadata-only items prevent this claim. If discovery is incomplete, analysis must also be incomplete. Runtime readiness remains separate even when static analysis is complete.
- `continuation`: `completed` and `remaining` (strings), `hypotheses` and `decisions` (strings), `revalidation` and `source_needs` (strings), `authorization_note` (string). Preserve decisions and concise rationale, not hidden chain-of-thought. Suggested next actions confer no authority to modify the target. Identify source bytes/access needed to continue.
- `extensions`: object for target-specific structures and definitions, including journeys, chronology, data lineage, permissions, topology, and refuted hypotheses.

## Collections

- `checks`: required check-coverage matrix. Each row has `id`, `category`, `title`, `status`, `scope`, `method`, `artifact_ids`, `evidence_ids`, `related_ids`, `verification_state`, `result`, `limitations`, `reason`, `next_step`. Apply the categories, status meanings, evidence rules and completeness semantics in `check-coverage.md`. Allowed statuses: `assessed`, `partial`, `not_assessed`, `blocked`, `not_applicable`. Allowed verification states: `static`, `observed`, `inferred`, `unverified`. Assessed/partial rows need substantive evidence; assessed cannot use unverified verification state. Unfinished rows need a nonempty next_step; assessed/not_applicable may use null. Required categories must all be represented; add target-specific categories freely. `related_ids` references findings, controls, unknowns or actions. Expose the same rows in a visible plain-language matrix.

- `artifacts`: `id`, `locator`, `type`, `status`, `reason`, `evidence_ids`, `inspection_origin`, `inspected_at`, `content_identity`. Use status `discovered`, `metadata_only`, `content_read`, `analyzed`, `partial`, `unreadable`, `excluded`, or `not_inspected`. `analyzed` means relevant semantics were examined, not verified correct. `inspection_origin` is `fresh`, `verified_reuse`, `unverified_carryover`, or `none`. `content_identity` is a hash/blob/version identity or a string explaining why unavailable. `inspected_at` is a timestamp, or null only for `none`. Include size/provenance when available. An analyzed artifact needs substantive evidence and fresh inspection or verified reuse. Include every discoverable member, not just deeply read files. If inventory itself cannot fit, explicitly declare incomplete discovery and the omitted boundary; do not call it a full handoff.
- `components`: `id`, `name`, `purpose`, `artifact_ids`, `evidence_ids`, `boundaries`. Include external systems as explicit components; empty artifact references are valid for them.
- `relationships`: `id`, `from_id`, `to_id`, `kind`, `explanation`, `evidence_ids`, `confidence`, `verification_state`. Endpoints reference artifacts/components. Every edge needs supporting evidence, including an explicit reasoning record for inference. Use verification state `static`, `observed`, `inferred`, or `unverified`; do not confuse an import with a proven deployed connection.
- `evidence`: `id`, `artifact_id`, `locator`, `kind`, `claim`, `result`, `method`, `time`, `limitations`, `inspection_origin`, `producer`, and `source_digest`. `producer` records kind/name/version; `source_digest` binds the observation to source identity. Kinds are `observed`, `static`, `inferred`, `unverified`; origins are `fresh`, `verified_reuse`, `unverified_carryover`. Use precise line/page/member/symbol/offset/URL locators. Results contain redacted excerpts, observations or reasoning supporting the claim. For external evidence, inventory its source as an artifact. Require `reuse` object for verified reuse: `prior_scan_id`, `prior_inspected_at`, `prior_method`, `prior_depth`, `prior_limits` (strings), `identity_check`, `identity_match` (true). Preserve the substantive evidence itself; an old report ID or unchanged HEAD alone is insufficient. Compare prior_depth with the original artifact status and inspected ranges. Reuse cannot promote a sampled/partial artifact to analyzed; retain the weaker supported depth when prior records conflict. A fresh complete analysis may replace that limit, but label it fresh rather than rewrite history.
- `findings`: `id`, `title`, `impact`, `severity`, `confidence`, `verification_state`, `artifact_ids`, `evidence_ids`, `uncertainty`, `recommendation`, `safe_verification`. Findings need evidence. Use severity `critical`, `high`, `medium`, `low`, `informational`; verification states as for relationships.
- `controls`: `id`, `description`, `artifact_ids`, `evidence_ids`, `effectiveness_status`, `limitations`. Require evidence. Status is `implemented_unverified`, `observed_effective`, `observed_failed`, or `reported_unverified`. Effective/failed status needs observed evidence with origin other than unverified carryover. Include environment, scope and date limits; a guard's presence or test definition is not a test result.
- `unknowns`: `id`, `question`, `artifact_ids`, `evidence_ids`, `reason`, `impact`, `next_safe_step`. Empty evidence is valid for explicitly unverified unknowns. Record inaccessible and unexamined areas and their consequences.
- `actions`: `id`, `description`, `priority`, `related_ids`, `prerequisites` (strings), `authorization_requirements` (string), `expected_verification` (string), `completion_state` (string).

## Delivery checks

Derive visible metrics from the final status/origin combinations: fresh analyzed excludes verified reuse, and analyzed excludes partial reads. Compare reused depth against the actual earlier record before accepting its provenance. Resolve references to the correct collection, not merely any existing ID. Verify critical-artifact coverage, counts, origins and substantiation. Evidence for an analyzed artifact must include its own artifact_id; a relevant imported dependency can have additional evidence.

Make the visible verdict, coverage and structured state agree. Display incomplete analysis near the verdict; call statically observed controls implemented rather than proven effective. Do not count sample reads as full semantic review. Preserve complete embedded inventory membership where discoverable, including generated, vendor, hidden, test and unsupported files; a tree hash and external links cannot stand in for rows.

Include human-readable instructions to locate the JSON and its schema version. A zero-context AI must be able to reconstruct the documented snapshot without fetching a previous report. State that the HTML cannot recreate missing source bytes. Check all this semantically after running the structural validator; passing validation cannot establish factual truth, adequate depth, execution safety or visual quality.

## Version transition

Historical Scan 1.3 added deterministic run/privacy/provenance fields and evidence producer/source-digest requirements on top of the 1.2 check-coverage contract. Treat older reports as historical input. Do not relabel a 1.1 or 1.2 report as 1.4 or infer checks were performed from artifact statuses. Build current records from actual evidence and record unperformed work honestly. Existing historical reports need not be rewritten solely because the skill changed.


## Current Scan 1.4 construction and continuation

Current authoring version: **1.4**. Historically accepted validation versions: **1.2, 1.3, 1.4**. The renderer supports historical 1.3 as well as current 1.4; historical 1.2 uses its frozen demo builder. Never upgrade a version label without constructing all current fields from evidence.

Create new state with `scan_project(ScanConfig(...))`, extend it with `SemanticStateBuilder`, call `build()`, then `render_report(state, output)`. The JSON is canonical; the HTML and its `{{STATE_SCHEMA_VERSION}}` label must come from that same state. New reports require all earlier core objects plus:

- `baseline`: `mode` (`auto`, `none`, `explicit`), `status` (`used`, `not_found`, `disabled`, `invalid`, `incompatible`), `source_schema_version`, `source_state_digest`, `source_snapshot_digest`, `snapshot_relation`, `reuse_enabled`, `fresh_evidence_count`, `reused_evidence_count`, `rejected_reuse_count`, `rejected_reuse_reasons`. Unused source fields are null, snapshot relation is `none`, and reused evidence count is zero. A used baseline must identify the exact source state and snapshot; relation may be `same`, `changed`, or `unknown`. Rejected reasons are reason-to-count records and sum to the rejected count. Counts refer to evidence records, not files or findings.
- `delta`: `available` plus `artifacts` (`added`, `changed`, `removed`, `unchanged`), `findings` (`new`, `persisting`, `modified`, `resolved`), and `unknowns` (`new`, `persisting`, `modified`, `resolved`). Lists contain stable IDs. Removed/resolved IDs belong to the baseline; they need not exist in the current state. Unavailable delta lists are empty. A resolved finding/unknown means absent from the current state, never proof of remediation or runtime verification. Compare `delta` before reading unchanged receipts.
- Every evidence row has `freshness`: `status`, `source_state_digest`, `source_evidence_id`, `original_observed_at`, `reused_at`, `reuse_reason`. Fresh rows use `status: fresh`, preserve `time` in `original_observed_at`, and use null for the four reuse-only fields. Reused rows use `status: verified_reuse`, preserve original time/method/depth/limits, identify the immediate baseline digest and evidence ID, and record the new reuse time and reason. They also retain the earlier `reuse` object and substantive evidence. Runtime/live/deployment/time-sensitive evidence is never automatically reused.
- Reuse candidates opt in with `evidence_class`, `check_id`, and `check_definition_digest`. The current invocation must explicitly register the exact producer kind/name/version and current check definitions; a baseline does not authorize its own producer. Content identity, producer version, check ID/definition, and current privacy must all match. No automatic artifact/check assessment or depth upgrade follows from reusing evidence. See `semantic-continuation.md` for the API.
- `extensions.git_change_scope`, when requested, records local Git `base_ref`, `head_ref`, `git_version`, `added`, `modified`, `deleted`, `renamed`, `copied`, `untracked`, and `limitations`. Rename/copy rows include `from`, `to`, and `similarity`. This is advisory prioritization context; full filesystem inventory remains authoritative. No remote fetch occurs. It is distinct from Scan's artifact delta and does not change stable artifact identity.
- Preserve `unknowns`, including open runtime, source-access, privacy, discovery, and semantic gaps. Registration/reuse does not resolve unknowns. Continue them with evidence or record their absence as a state delta only.

### Visible count markers

Current HTML requires exactly one `data-scan-count` marker for each renderer count, with integer text matching canonical records: `discovered_artifact_count`, `content_read_count`, `checks_assessed`, `finding_count`, `redaction_count`, `unknown_count`, `delta_artifacts_added`, `delta_artifacts_changed`, `delta_artifacts_removed`, `delta_findings_new`, `delta_findings_resolved`, `delta_unknowns_new`, `delta_unknowns_resolved`, `fresh_evidence_count`, `reused_evidence_count`, `rejected_reuse_count`. Do not nest or duplicate markers. Historical 1.3 uses its original six-marker contract; 1.2 validation retains its historical rules. Counts are reconciliation aids, never proof of claim accuracy. Keep fresh/reused, metadata-only, partial, unassessed and runtime coverage distinct. Without a defensible denominator, show qualitative status rather than a numerical percentage.

### Static self-contained HTML safety

`scan validate` parses HTML without executing it or making network requests. For all accepted schema versions it permits exactly the authoritative inert `application/json` script, inline CSS, native static HTML/disclosure, fragment anchors and ordinary HTTP(S)/mailto evidence links. Embedded raster image data is allowed; linked resources (including relative files), extra scripts (even JSON), event attributes, active URI schemes, CSS resource references/imports, CSS expression/binding/behavior mechanisms, foreign SVG/MathML surfaces, forms, base/refresh, plugins and frames are rejected. CSS resource syntax is conservatively rejected even if a particular URL might be local. No script or fetched stylesheet is needed to read a report. This deliberately narrow contract is not a general HTML sanitizer.

Unsafe/non-self-contained HTML raises `UnsafeReportError` (a `ValidationError`) with an explicit safety diagnostic. Missing/malformed state, broken typed references and mismatched counts remain structural validation failures. Structural validity establishes neither factual correctness nor adequate review depth.
